# 07 · π₀.₅: a large vision-language-action model

**English** · [简体中文](07_pi05.zh-CN.md)

Paper: Physical Intelligence, *π₀.₅: a Vision-Language-Action Model with Open-World Generalization*, 2025
([arXiv:2504.16054](https://arxiv.org/abs/2504.16054)). LeRobot's implementation is ported from the official [openpi](https://github.com/Physical-Intelligence/openpi).

PS: training is done (3000 steps on an A100 via HF Jobs, about 7 h) and the offline check passes; the model doesn't fit the laptop's GPU, so inference runs on a cloud GPU (§8).

## 1. Compared with SmolVLA

Same idea in both: **a VLM reads the images and text, an action expert generates a 50-step chunk with flow matching**
(flow matching is explained in [06_smolvla.md](06_smolvla.md) §3). The differences are scale and a few design choices:

| | SmolVLA | π₀.₅ |
|---|---|---|
| VLM | SmolVLM2-500M (first 16 layers only) | **PaliGemma**: SigLIP So400m + Gemma 2B (all 18 layers) |
| Action expert | Transformer of width 720 | Gemma 300M shape (width 1024, 18 layers) |
| How the two talk | alternating cross- / self-attention | **joint attention in every layer** (§2.3) |
| How time $t$ enters | concatenated into the action tokens | **adaRMSNorm**: modulates every layer's normalisation |
| How the joint state enters | linear projection into one token | **discretised into text** in the prompt |
| Parameters | ~450M | **~4.1B** |
| Trained during fine-tuning | action expert only (~100M) | **everything** |
| Image size | 512×512 | 224×224 |
| Pretraining data | community LeRobot datasets | Physical Intelligence's own large multi-robot data + web image-text data |

## 2. Architecture

```
 prefix: processed by PaliGemma                            suffix: processed by the action expert
┌────────────────────────────────────────────────────┐   ┌─────────────────────────────┐
│ image tokens: 256 each × 3 slots                    │   │ 50 action tokens             │
│ text tokens: "Task: ..., State: 128 97 ...;\nAction:"│   │ = noisy actions (Linear → 1024)│
└────────────────────────────────────────────────────┘   └─────────────────────────────┘
        Gemma 2B: 18 layers, width 2048   ◀── joint attention in every layer ──▶   Gemma 300M: 18 layers, width 1024
                                                                   ↑ time t → MLP → adaRMSNorm
                                                                   │
                                                     Linear → velocity field v, 50 × 32 (first 6 used)
```

### 2.1 PaliGemma: the VLM

Same recipe as SmolVLM, "ViT + projection + language model", only bigger:

1. **SigLIP So400m** (a ViT, ~400M parameters, patch 14): a 224×224 image becomes 16×16 = **256 patch tokens**, no compression.
2. **Linear projection** of each visual token to Gemma's width, 2048.
3. **Gemma 2B** (18 layers, width 2048, 8 attention heads, 1 KV head, i.e. MQA) processes the prefix of image tokens + text tokens.

PS: PaliGemma is a **prefix-LM**: tokens in the prefix attend **bidirectionally** (like BERT); only what is generated after it is causal.
So images and instruction see each other rather than only "looking backwards".

### 2.2 The joint state written as text

π₀.₅ doesn't give the state its own input channel; it **writes it into the prompt**:

1. the state is quantile-normalised to [−1, 1];
2. [−1, 1] is split into 256 equal bins, so each joint becomes an integer 0–255;
3. it becomes a sentence, `Task: pick up the blue plush toy..., State: 128 97 200 ...;\nAction: `, which is then tokenised.

The starting point: what a language model is best at is reading token sequences. So let it read the robot state as numbers, together with the instruction.
Limit: 256 bins (about 0.008 per bin on [−1, 1]) is coarser than a continuous value, but enough for "roughly what pose are we in"; the fine motion is the action expert's job.

### 2.3 Joint attention: two experts sharing one attention

In π₀ / π₀.₅ the action expert and the VLM are **two sets of Transformer weights with the same number of layers**, but each layer's attention is **computed together**:

1. prefix tokens compute Q, K, V with Gemma 2B's weights; suffix (action) tokens compute Q, K, V with Gemma 300M's weights.
   Both use a head dimension of 256, so they can be concatenated.
2. The two sets of Q, K, V are **concatenated into one sequence** and attention is computed **once**.
3. The output is split again: the prefix part goes through Gemma 2B's FFN, the suffix part through Gemma 300M's FFN.

So it is a mixture of experts "routed by token type": one attention, different FFNs and projections.
In every layer the action tokens directly see that layer's VLM features.

Mask rule:

| Who sees whom | prefix (images + text) | actions |
|---|---|---|
| prefix | ✓ (bidirectional) | ✗ |
| actions | ✓ | ✓ (bidirectional among the 50 action tokens) |

As in SmolVLA, **the prefix can't see the actions**, so at inference the prefix is computed once and kept as a KV cache, and the 10 integration steps only run the action expert.

### 2.4 adaRMSNorm: how time $t$ gets in

Flow matching has to tell the network "how noisy is it now" (time $t$). π₀.₅ doesn't concatenate $t$ into the tokens; it uses **adaRMSNorm**:

1. $t$ gets a sinusoidal encoding and goes through a two-layer MLP, giving a condition vector;
2. in every layer of the action expert, the RMSNorm scale is no longer a fixed learned parameter but **computed from** that condition vector (plus a gate that multiplies the residual branch).

PS: it is the same idea as FiLM in Diffusion Policy: the condition isn't an input, it modulates the scale of every layer's features. The adaLN in image-diffusion DiTs works the same way.

### 2.5 Training and inference

Exactly the same flow matching as SmolVLA: in training $A^t = t\,\epsilon + (1-t)\,A$, loss $\|v_\theta - (\epsilon - A)\|^2$, $t \sim$ Beta(1.5, 1);
at inference start from noise and take 10 Euler steps. State and action are zero-padded to 32 dimensions; the first 6 of the output are used.

PS: during pretraining π₀.₅ also learns discrete action tokens (FAST tokenisation) and text prediction of sub-tasks, which is part of where its generalisation comes from.
For fine-tuning LeRobot only uses the flow-matching objective.

## 3. Cameras: three input slots, we use two

The pretrained π₀.₅ was designed for a two-armed robot and has 3 image slots:

| Slot | Original use | What we plug in |
|---|---|---|
| `base_0_rgb` | main view | overhead camera `top` |
| `left_wrist_0_rgb` | left wrist | wrist camera `wrist` |
| `right_wrist_0_rgb` | right wrist | empty |

For a missing slot LeRobot inserts an image of all −1 and sets its **mask to 0**, telling the model "no image here", so attention ignores it.
That is how every single-arm robot uses it.

The mapping is given in `--rename_map` and saved into the model's preprocessing config (`policy_preprocessor.json`) during training,
so **it applies automatically at deployment**.

## 4. Why rent a GPU

Memory for full fine-tuning in float32:

| Item | Size |
|---|---|
| weights: 4.1B × 4 bytes | 16.6 GB |
| gradients | 16.6 GB |
| AdamW's two states (first and second moments) | 33 GB |
| activations (with gradient checkpointing) | a few GB |
| **total (measured)** | **66.9 GB** |

Neither the laptop (8 GB) nor a 16 GB V100 can hold it, so we rent an **A100 80 GB** on Hugging Face Jobs ($2.50/hour).

Why not bf16 to save memory? LeRobot's bf16 mode stores most of the weights themselves in bf16. Once the learning rate decays to around 1e-6,
many parameter updates are smaller than bf16's precision and get rounded away. Our rule is "change the original method as little as possible", so we keep float32 and shorten training instead (§5).

## 5. Training config

Compared with LeRobot's defaults, **only the number of steps changes**:

| Parameter | Value | Note |
|---|---|---|
| pretrained weights | `lerobot/pi05_base` | |
| precision | float32 | default |
| batch size | 32 | default |
| steps | **3000** (default 30000) | the default would take ~70 h and $175; 3000 steps take ~7 h |
| LR decay steps | **3000** (default 30000) | follows the step count so the cosine reaches its minimum at the end |
| learning rate | peak 2.5e-5 → final 2.5e-6, AdamW (0.9, 0.95), weight decay 0.01, grad clip 1.0 | default |
| warm-up | 1000 steps | default, not changed, so it takes the first third of training |
| action chunk | predict 50, execute 50; 10 integration steps at inference | default |
| normalisation | quantile normalisation for state and action | default |

3000 steps × batch 32 = 96k samples, about 5.6 epochs.
This is a **reduced budget**: if it does worse on the robot than the other policies, we can't tell whether the method or the short training is to blame, and the report has to say so.

## 6. Training on HF Jobs

[`cloud/hf_jobs/train_pi05.py`](../cloud/hf_jobs/train_pi05.py) submits the job from the laptop using LeRobot's own
`--job.target=<hardware>`: the laptop only resolves the config and uploads it to a new private model repo; training runs on HF's machines
and pushes the model back to that repo. The code is explained in [code_walkthrough.md §13](code_walkthrough.md).

Before the first run:

1. Credit on the Hugging Face account.
2. A token with **write** access. A fine-grained token also needs the Jobs permission. Log in with `hf auth login` in the terminal; never write the token into a file.
3. Accept the licence of [`google/paligemma-3b-pt-224`](https://huggingface.co/google/paligemma-3b-pt-224) on the website: π₀.₅ uses its tokenizer.
   Without it the job fails with 403 while downloading.

Commands:

```powershell
python cloud/hf_jobs/train_pi05.py --dry-run                     # print the job config, don't submit
python cloud/hf_jobs/train_pi05.py --steps 200 --timeout 40m     # measure speed and memory first
python cloud/hf_jobs/train_pi05.py --steps 3000 --timeout 9h     # the real run
```

Progress:

```powershell
hf jobs ps -a                  # state: RUNNING / COMPLETED / ERROR / CANCELED
hf jobs logs <job_id>          # log (loss every 100 steps)
```

PS:

- `--timeout` doesn't include **queueing**. A100s sometimes queue for over an hour; queueing isn't billed.
- On Windows LeRobot writes the model id as `lerobot\pi05_base` (backslash), which the Linux job can't find, so the script turns it back into a slash before uploading the config.
- The Windows terminal uses GBK, and characters like ✓ in `hf jobs` output make it fail with `'gbk' codec can't encode`.
  Set `$env:PYTHONUTF8 = "1"` first (`scripts/env.ps1` does it).

| 500 | 1.0 | 0.043 | 0.33 | 1.1e-5 |

| 3000 | 5.6 | **0.008** | 0.13 | 2.6e-6 |

- 8.4 s per step, 67.2 GB of VRAM, 7 h 06 min in total, about **$17.8**.
- A smooth loss curve without spikes; the gradient norm keeps falling.
- This loss is the flow-matching velocity error and **can't be compared with ACT's or Diffusion's loss** (different definitions).
  Training used all 50 demos with no validation split, so a low loss only says it fits well. The real-robot success rate decides.

## 8. Deployment: inference in the cloud

Inference is only a forward pass, but even bf16 weights are about 8.3 GB, more than the laptop's 8 GB.
Offloading layers to the CPU would be too slow for control, and quantisation changes the model. So we use LeRobot 0.7's built-in **remote inference**:

```
laptop (arm + cameras)                               cloud GPU (≥ 24 GB)
lerobot-rollout --inference.type=remote   ──►   lerobot-policy-server
  sends: both images (JPEG) + joint angles          loads π₀.₅, predicts 50 actions
  receives: the chunk, executed at 30 Hz    ◄──
```

- It talks over TCP (default `127.0.0.1:7447`); an **SSH tunnel** maps the cloud port to the laptop, so no public port is opened.
- One request ≈ network round trip + inference, usually under 0.5 s. A chunk lasts 1.67 s and LeRobot asks for the next one 0.5 s early,
  so the arm never stops to wait.
- HF Jobs can't do this (no SSH, nothing can connect in). You need an hourly GPU VM with SSH access:
  a 24 GB card holds the float32 weights, identical to training. 40 trials plus debugging take about 2 h, a dollar or two.
- The cloud side must run the same LeRobot version (0.7.0): the remote-inference protocol is versioned, and mismatched sides won't connect.

### Offline check (laptop CPU)

After downloading, first check the SHA-256 of `model.safetensors` against the Hub: identical. The laptop's RAM can't hold two float32 copies,
so the model is built in bf16 and the tensors are copied in from the file one by one (813, none missing); loading takes about 6 minutes.

One frame from each of 5 demos (before grasp, grasping, carrying, releasing); predict a 50-step chunk and compare with the recorded actions.
Mean absolute error per joint (degrees; gripper 0–100):

| | pan | lift | elbow | wrist flex | wrist roll | gripper | mean |
|---|---|---|---|---|---|---|---|
| π₀.₅ | 0.9 | 3.4 | 3.3 | 1.1 | 0.8 | 0.4 | **1.7** |
| baseline: hold still | 14.2 | 29.3 | 31.2 | 13.1 | 3.2 | 7.3 | 16.4 |

- The model loads correctly and its actions match the demos closely. The largest error is at the first frame (lift and elbow about 8° each, starting from rest), because when to start moving is genuinely uncertain.
- These frames are in the training set, so this only proves **the model isn't broken**, not that it generalises.
- On the CPU one chunk takes **about 186 s**, over 100× slower than the 1.67 s control needs, so the robot needs a GPU.
