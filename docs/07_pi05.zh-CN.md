# 07 · π₀.₅：大型视觉-语言-动作模型

[English](07_pi05.md) · **简体中文**

论文：Physical Intelligence, *π₀.₅: a Vision-Language-Action Model with Open-World Generalization*, 2025
（[arXiv:2504.16054](https://arxiv.org/abs/2504.16054)）。LeRobot 里的实现移植自官方的 [openpi](https://github.com/Physical-Intelligence/openpi)。

PS：训练完成（3000 步，HF Jobs 上的 A100，约 7 小时），离线检查通过；笔记本显存放不下，推理要放到云端 GPU 上（第 8 节）。

## 1. 和 SmolVLA 比

两者的思路一样：**VLM 处理画面和文字，动作专家用 flow matching 生成 50 步动作块**（flow matching 见 [06_smolvla.zh-CN.md](06_smolvla.zh-CN.md) 第 3 节）。
区别在规模，以及几个设计选择：

| | SmolVLA | π₀.₅ |
|---|---|---|
| VLM | SmolVLM2-500M（只用前 16 层） | **PaliGemma**：SigLIP So400m + Gemma 2B（18 层全用） |
| 动作专家 | 宽 720 的 Transformer | Gemma 300M 结构（宽 1024，18 层） |
| 两者怎么交流 | 交替的 cross-attention / self-attention | **每一层都做联合注意力**（第 2.3 节） |
| 时间 $t$ 怎么输入 | 拼进动作 token | **adaRMSNorm**：调节每一层的归一化 |
| 关节状态怎么输入 | 线性层投影成一个 token | **离散成文字**，写进提示词 |
| 总参数 | ~4.5 亿 | **~41 亿** |
| 微调时训练哪些 | 只训动作专家（~1 亿） | **全部参数** |
| 输入图像 | 512×512 | 224×224 |
| 预训练数据 | 社区上传的 LeRobot 数据集 | Physical Intelligence 自己的大规模多机器人数据 + 网络图文数据 |

## 2. 结构

```
 前缀（prefix）：PaliGemma 处理                         后缀（suffix）：动作专家处理
┌──────────────────────────────────────────────────┐   ┌─────────────────────────────┐
│ 图像 token：每张 256 个 × 3 个槽位                  │   │ 50 个动作 token              │
│ 文字 token："Task: ..., State: 128 97 ...;\nAction:"│   │ = 噪声动作（Linear → 1024）   │
└──────────────────────────────────────────────────┘   └─────────────────────────────┘
        Gemma 2B：18 层，宽 2048        ◀── 每层联合注意力 ──▶   Gemma 300M：18 层，宽 1024
                                                                   ↑ 时间 t → MLP → adaRMSNorm
                                                                   │
                                                     Linear → 50 × 32 的速度场 v（取前 6 维）
```

### 2.1 PaliGemma：VLM 部分

结构和 SmolVLM 一样是 "ViT + 投影层 + 语言模型"，只是更大：

1. **SigLIP So400m**（ViT，约 4 亿参数，patch 14）：224×224 的图像切成 16×16 = **256 个 patch token**，不再压缩。
2. **线性投影**：把每个视觉 token 映射到 Gemma 的宽度 2048。
3. **Gemma 2B**（18 层，宽 2048，8 个注意力头，1 个 KV 头，即 MQA）：处理"图像 token + 文字 token"组成的前缀。

PS：PaliGemma 是一个 **prefix-LM**：前缀里的 token 之间是**双向注意力**（像 BERT），只有之后生成的部分才是因果的。
所以图像和指令可以互相看到，而不是只能"往前看"。

### 2.2 关节状态写成文字

π₀.₅ 不给状态单独开一个输入通道，而是把它**写进提示词**：

1. 状态先用分位数归一化到 [−1, 1]；
2. 把 [−1, 1] 均匀分成 256 档，每个关节变成 0–255 之间的一个整数；
3. 拼成一句话：`Task: pick up the blue plush toy..., State: 128 97 200 ...;\nAction: `，再分词。

出发点是：语言模型最擅长的就是读 token 序列。既然如此，就让它用"读数字"的方式读机器人状态，和指令一起理解。
Limit：256 档的分辨率（[−1, 1] 上每档约 0.008）比连续值粗，但对"现在大概在什么姿态"已经够用了；精细的动作由动作专家负责。

### 2.3 联合注意力：两个专家共用一个注意力

π₀ / π₀.₅ 的动作专家和 VLM 是**同样层数的两套 Transformer 权重**，但每一层的注意力是**合在一起算**的：

1. 前缀 token 用 Gemma 2B 的权重算 Q、K、V；后缀（动作）token 用 Gemma 300M 的权重算 Q、K、V。
   两者的 head 维度都是 256，所以可以拼在一起。
2. 把两组 Q、K、V **拼成一个序列**，做**一次**注意力。
3. 输出再拆开，前缀的部分走 Gemma 2B 的 FFN，后缀的部分走 Gemma 300M 的 FFN。

所以它其实是一种"按 token 类型路由"的 mixture of experts：同一个注意力，不同的 FFN 和投影。
动作 token 在每一层都能直接看到 VLM 那一层的特征。

Mask 规则：

| 谁能看谁 | 前缀（图像 + 文字） | 动作 |
|---|---|---|
| 前缀 | ✓（双向） | ✗ |
| 动作 | ✓ | ✓（50 个动作 token 之间双向） |

和 SmolVLA 一样，**前缀看不到动作**，所以推理时前缀只算一次、存成 KV cache，10 步积分只跑动作专家。

### 2.4 adaRMSNorm：时间 $t$ 怎么进去

Flow matching 要告诉网络"现在噪声有多大"（时间 $t$）。π₀.₅ 没有把 $t$ 拼进 token，而是用 **adaRMSNorm**：

1. $t$ 先做正弦编码，再过两层 MLP，得到一个条件向量；
2. 动作专家的每一层里，RMSNorm 的缩放不再是固定的可学习参数，而是由这个条件向量**算出来的**（还有一个门控系数乘在残差分支上）。

PS：这和 Diffusion Policy 里的 FiLM 是同一个思想：条件不作为输入，而是去调节每一层特征的尺度。图像扩散里的 DiT 用的 adaLN 也是这样。

### 2.5 训练和推理

和 SmolVLA 完全一样的 flow matching：训练时 $A^t = t\,\epsilon + (1-t)\,A$，损失 $\|v_\theta - (\epsilon - A)\|^2$，$t \sim$ Beta(1.5, 1)；
推理时从噪声出发，欧拉法积分 10 步。状态和动作都补零到 32 维，输出取前 6 维。

PS：π₀.₅ 在预训练时还会同时学"离散的动作 token"（FAST 分词）和"子任务的文字预测"，这是它泛化能力的一部分来源。
微调时 LeRobot 只用 flow matching 这一个目标。

## 3. 相机：三个输入槽，我们用两个

π₀.₅ 的预训练模型按双臂机器人设计，有 3 个图像槽：

| 槽位 | 原本用途 | 我们接的 |
|---|---|---|
| `base_0_rgb` | 主视角 | 俯视相机 `top` |
| `left_wrist_0_rgb` | 左手腕 | 腕部相机 `wrist` |
| `right_wrist_0_rgb` | 右手腕 | 空 |

缺少的槽位，LeRobot 会填一张全是 −1 的空图，并把它的**掩码设为 0**，告诉模型"这一路没有画面"，注意力不会看它。
单臂机器人都这么用。

对应关系写在 `--rename_map` 里，训练时会存进模型的预处理配置（`policy_preprocessor.json`），
所以**部署时会自动套用**，不用再传一次。

## 4. 为什么要租 GPU

全量微调 float32 的显存估算：

| 项 | 大小 |
|---|---|
| 权重：41 亿 × 4 字节 | 16.6 GB |
| 梯度 | 16.6 GB |
| AdamW 的两个状态（一阶、二阶矩） | 33 GB |
| 激活（开了梯度检查点） | 几 GB |
| **合计（实测）** | **66.9 GB** |

笔记本（8 GB）和集群上能用的 V100（16 GB）都放不下，所以在 Hugging Face Jobs 上租 **A100 80 GB**（$2.50/小时）。

为什么不用 bf16 省显存？LeRobot 的 bf16 模式会把大部分权重本身存成 bf16。学习率衰减到 1e-6 量级时，
很多参数的更新量比 bf16 能表示的精度还小，会被直接舍掉。我们的原则是"和原方法改动最小"，所以保留 float32，改成缩短训练步数（第 5 节）。

## 5. 训练配置

和 LeRobot 默认配置相比，**只改了步数**：

| 参数 | 值 | 说明 |
|---|---|---|
| 预训练权重 | `lerobot/pi05_base` | |
| 精度 | float32 | 默认 |
| batch size | 32 | 默认 |
| 步数 | **3000**（默认 30000） | 默认要约 70 小时、$175；3000 步约 7 小时 |
| 学习率衰减步数 | **3000**（默认 30000） | 跟着步数改，余弦曲线在训练结束时降到最低 |
| 学习率 | 峰值 2.5e-5 → 最终 2.5e-6，AdamW (0.9, 0.95)，权重衰减 0.01，梯度裁剪 1.0 | 默认 |
| 预热 | 1000 步 | 默认值，没跟着改，所以占了训练的前三分之一 |
| 动作块 | 预测 50 步，执行 50 步；推理时积分 10 步 | 默认 |
| 归一化 | 状态和动作用分位数（quantile）归一化 | 默认 |

3000 步 × batch 32 = 9.6 万个样本，约 5.6 个 epoch。
这是**缩减过的预算**：如果真机效果不如别的策略，分不清是方法本身的问题还是训练不够，报告时要写明。

## 6. 在 HF Jobs 上训练

脚本 [`cloud/hf_jobs/train_pi05.py`](../cloud/hf_jobs/train_pi05.py) 从笔记本提交任务，用的是 LeRobot 自带的
`--job.target=<硬件>`：本机只解析配置、上传到一个新的私有模型仓库，真正的训练在 HF 的机器上跑，
训完把模型推回这个仓库。代码讲解见 [code_walkthrough.zh-CN.md 第 13 节](code_walkthrough.zh-CN.md)。

第一次之前要准备：

1. Hugging Face 账号里有余额。
2. 一个有**写**权限的 token。细粒度（fine-grained）token 还要勾上 Jobs 权限。在终端里运行 `hf auth login` 登录，
   token 不要写进任何文件。
3. 在网页上同意 [`google/paligemma-3b-pt-224`](https://huggingface.co/google/paligemma-3b-pt-224) 的许可：π₀.₅ 用它的分词器。
   没同意的话任务会在下载时报 403。

**命令：**

```powershell
python cloud/hf_jobs/train_pi05.py --dry-run                     # 只打印任务配置，不提交
python cloud/hf_jobs/train_pi05.py --steps 200 --timeout 40m     # 先测速度和显存
python cloud/hf_jobs/train_pi05.py --steps 3000 --timeout 9h     # 正式训练
```

查看进度：

```powershell
hf jobs ps -a                  # 状态：RUNNING / COMPLETED / ERROR / CANCELED
hf jobs logs <job_id>          # 日志（含每 100 步的 loss）
```

PS：

- `--timeout` 不包括**排队**时间。A100 有时要排一个小时以上，排队期间不计费。
- 在 Windows 上，LeRobot 会把模型 id 写成 `lerobot\pi05_base`（反斜杠），Linux 上的任务就找不到模型，所以脚本在上传配置前把它改回了斜杠。
- Windows 终端是 GBK 编码，`hf jobs` 输出里的 ✓ 之类字符会让它报 `'gbk' codec can't encode`。
  先设 `$env:PYTHONUTF8 = "1"`（`scripts/env.ps1` 已经设了）。

## 7. 训练结果

| 步数 | epoch | loss | 梯度范数 | 学习率 |
|---|---|---|---|---|
| 100 | 0.2 | 0.188 | 1.57 | 1.3e-6（预热中） |
| 500 | 1.0 | 0.043 | 0.33 | 1.1e-5 |
| 1000 | 2.1 | 0.027 | 0.19 | 1.9e-5 |
| 2000 | 4.0 | 0.012 | 0.14 | 7.6e-6 |
| 3000 | 5.6 | **0.008** | 0.13 | 2.6e-6 |

- 每步 8.4 秒，显存 67.2 GB，总运行 7 小时 6 分，约 **$17.8**。
- loss 曲线平滑，没有跳动；梯度范数持续下降。
- 这个 loss 是 flow matching 的速度误差，**不能和 ACT、Diffusion 的 loss 比**（定义不同）。
  而且这次用全部 50 条示范训练，没有留验证集，loss 低只说明拟合得好。最终看真机成功率。

模型在私有仓库 `Yufeng1216/pi05_so101_pick_place_2026-11-24_22-52-17`（16.6 GB，float32）。下载到本地：

## 8. 部署：推理放到云端

推理只需要前向计算，但 bf16 的权重也要约 8.3 GB，笔记本的 8 GB 显存放不下。
把一部分层放到 CPU 上会慢到跟不上控制；量化会改变模型。所以用 LeRobot 0.7 自带的**远程推理**：

```
笔记本（机械臂 + 相机）                              云端 GPU（≥ 24 GB）
lerobot-rollout --inference.type=remote   ──►   lerobot-policy-server
  发送：两路画面（JPEG）+ 关节角                     加载 π₀.₅，预测 50 步动作
  收到：动作块，按 30 Hz 执行               ◄──
```

- 通信走 TCP（默认 `127.0.0.1:7447`），用 **SSH 隧道**把云端端口映射到本机，云上不用开公网端口。
- 一次请求 ≈ 网络往返 + 推理，一般在 0.5 秒以内；一个动作块能执行 1.67 秒，LeRobot 还会提前 0.5 秒请求下一块，
  所以机械臂不会停下来等。
- HF Jobs 不能用来做这个（没有 SSH，外部连不进去）。要租按小时计费、能 SSH 登录的 GPU 云主机：
  24 GB 的卡能直接放下 float32 权重，和训练时完全一致。评估 40 次加调试约 2 小时，一两美元。
- 云端必须装同一个版本的 LeRobot（0.7.0）：远程推理协议带版本号，两边不一致连不上。

### 离线检查（笔记本 CPU）

下载后先核对 `model.safetensors` 的 SHA-256，和 Hub 上一致。笔记本内存放不下 float32 的两份拷贝，
所以用 bf16 建模型，再从文件里逐个张量拷进去（813 个，没有缺失），加载约 6 分钟。

从 5 条示范里各取一帧（抓取前、抓取中、搬运中、放下时），预测 50 步动作块，和示范里记录的动作比，
每个关节的平均绝对误差（度；夹爪是 0–100）：

| | 底座 | 大臂 | 小臂 | 腕俯仰 | 腕旋转 | 夹爪 | 平均 |
|---|---|---|---|---|---|---|---|
| π₀.₅ 预测 | 0.9 | 3.4 | 3.3 | 1.1 | 0.8 | 0.4 | **1.7** |
| 对照：原地不动 | 14.2 | 29.3 | 31.2 | 13.1 | 3.2 | 7.3 | 16.4 |

- 模型加载正确，预测的动作和示范基本吻合。误差最大的是第一帧（静止起步时大臂、小臂各约 8°），因为从哪一刻开始动本来就不确定。
- 这些帧都在训练集里，所以这只能证明**模型没坏**，不能说明泛化能力。
- CPU 上一个动作块要 **约 186 秒**，比控制需要的 1.67 秒慢 100 多倍，所以真机必须用 GPU。
